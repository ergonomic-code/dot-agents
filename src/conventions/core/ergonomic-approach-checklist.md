# Чек-лист эргономичного подхода

## Порядок разработки

- Если для изменения поведения было принято решение написать тест, то:
  - он был написан и запущен до внесения правок и завершился ожидаемой ошибкой,
  - либо после написания правок, продакшн код был временно сломан, а тест — запущен и завершился ожидаемой ошибкой.
  
## Общие правила

- Каждое изменение кода реализации служит требуемому поведению, а не только прохождению тестов.
- Смысловое дублирование определений и ответственностей устранено целиком, включая выраженное разным кодом.
- Итоговые изменения используют существующий код и определения без ненужного копирования, дублирования и преждевременных абстракций.
- Решение остаётся простым и не содержит функциональности или обработки маловероятных сценариев без текущей потребности или подтверждения пользователя.
- В зависимостях затронутых классов, модулей и сервисов нет циклов.

## Дизайн API методов

- Логика и действия разделены.
- Когнитивная сложность кода, прямо или косвенно выполняющего действия, не превышает четырёх единиц.
- Команды и запросы разделены; их побочные эффекты и возвращаемые значения соответствуют правилам CQS и оговорённым исключениям.
- В нетривиальных операциях выделена оркестрация потока данных и управления от чтения через преобразование к записи.
- Каждый изменённый метод имеет высокую связанность (high cohesion): выполняет одну согласованную задачу.
- Каждый изменённый метод проще использовать правильно, чем неправильно.

## Реализация методов

- Там где это возможно, используется функциональный стиль.
- Там где это возможно, обязательный порядок вызовов выражен через API методов.
- Открытием и закрытием каждого ресурса управляет один метод, если владение явно не передано.
- Реализация каждого изменённого метода не смешивает более двух уровней абстракции (терминов из разных словарей/доменов).
- Там где это возможно, глубокая вложенность кода устранена.

## Дизайн классов

- Все методы изменённого класса используют все его поля
- Всё API класса выражено на одном уровне абстракции.

## Дизайн данных

- Данные неизменяемы.
- Невозможно создать экземпляр класса или структуры данных, представляющих недопустимое состояние.
- Область допустимых значений для каждого поля не зависит от значений других полей.
- Значения с особым смыслом, единицей измерения, диапазоном или допустимостью `null` представлены семантическими типами либо явно обозначены на границах, где нужны примитивы.
