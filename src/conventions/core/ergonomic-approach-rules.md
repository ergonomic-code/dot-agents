# Общая философия кодирования Эргономичного подхода

## Порядок разработки

Старайся работать по TDD: писать и запускать тест, показывающий отсутствие требуемого поведения, до изменения продакшн-кода.

Тест можно не писать, если тестируемое поведение не является критически важным, а сам тест:
- не типичен для проекта, 
- или требует новой для проекта инфраструктуры или подхода, 
- или в среднем будет работать более 50 мс или запускаться более 10 секунд, 
- или требует вспомогательного кода в два раза больше чем целевой продакшн-код и код тест-кейса, 
- или по какой-то другой причине имеет повышенную сложность, которая не перевешивается его ценностью.

## Общие правила

- DRY.
  Не допускай дублирования в том числе и на семантическом уровне, даже если копии выражены разным синтаксисом.
  Исключение — код тест-кейсов, в них предпочитай DAMP и возможность понять смысл кейса только из кода самого кейса.
- YAGNI.
  Не вводи абстракции (интерфейсов, промежуточных слоёв, точек расширения и т.п.) до тех пор, пока в них нет действительной необходимости.
  Не реализуй функциональность без текущей потребности в ней.
- KISS.
  Предпочитай простое решение, в том числе требующее при прочих равных меньше кода.
  Не обрабатывай и не учитывай маловероятные сценарии без явного запроса или подтверждения пользователя.
- Не допускай циклических зависимостей между классами, модулями и сервисами.

## Дизайн API методов

- Разделяй логику и действия (IO, изменение глобального состояния, запуск потоков и процессов и т.п.).
  Код, прямо или косвенно выполняющий действия должен иметь когнитивную сложность не более четырёх единиц.
- CQS.
  Разделяй команды и запросы: команды изменяют состояние, а запросы только возвращают данные.
  - Команда может вернуть созданные в ходе её работы данные — например, идентификатор, значение по умолчанию, время, статус или результат — и, при необходимости, переданные ей данные.
    Не возвращай из команды данные, прочитанные извне в ходе её работы; исключение — операции вроде `putIfAbsent` и другие операции сравнения и замены.
  - Запрос не меняет состояние.
    Исключения — явно требуемая фиксация факта вызова и изменение внутреннего состояния, не влияющее на результат следующего вызова.
- Стремись делать форму операций системы сбалансированной — выделяй оркестрацию в отдельный метод, который определяет потоки данных и управления от действий чтения, через функции трансформации к действиям записи.
- High cohesion.
  Обеспечивай высокую связность методов: каждый метод должен выполнять одну согласованную задачу.
- Соблюдай принцип ямы успеха (Pit of success).
  Проектируй методы так, чтобы их было проще использовать правильно, чем неправильно.

## Реализация методов

- Предпочитай функциональный стиль императивному.
  - Избегай неявной зависимости от порядка вызовов: если один метод должен (MUST) вызываться после другого, делай этот порядок вызовов единственно возможным для компиляции, либо делай его явным через требование результата первого метода в качестве параметра второго метода.
- Открывай и закрывай ресурс в одном методе, если владение им явно не передаётся другому коду.
- Не смешивай в реализации функции более двух уровней абстракции (терминов из разных словарей/доменов — например HTTP и SQL, или предметной области и многопоточности).
- Избегай глубокой вложенности в методах.
  Для ошибочных и специальных состояний используй раннюю эвакуацию из методов с помощью охранных выражений (guard clauses — `if (somethingWrong) return/throw`).

## Дизайн классов 

- Обеспечивай высокую связность класса: все его методы должны использовать все его поля.
- Выражай всё API класса на одном уровне абстракции.

## Дизайн данных

- Делай данные неизменяемыми.
- Не допускай функциональных зависимостей между полями, когда допустимость значения одного поля определяется значением другого.
- Make Illegal States Unrepresentable.
  Проектируй классы и структуры данных так, чтобы нельзя было создать экземпляр в недопустимом состоянии.
