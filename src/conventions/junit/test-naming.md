# Именование тестов JUnit

Ориентируйся на соседние тесты только после применения этих правил, чтобы сохранить локальные механизмы, импорты, аннотации и стиль отчётов.

## Контейнеры

- Выбирай технический контейнер только после определения вида теста и SUT.
- Для HTTP-границы используй в качестве `<OperationName>` точное имя класса единственной прикладной операции, вызываемой эндпоинтом; если он вызывает ноль или несколько операций, используй имя метода обработчика с заглавным первым символом; назови контейнер `<OperationName>ApiTest`.
- Для другой границы выводи контейнер из идентификатора внешней операции и принятого в репозитории шаблона для этой границы; остановись, если шаблон нельзя определить однозначно.
- Для компонентного SUT `<ClassName>` выбери или создай `<ClassName>Test`; для `<ClassName>.<methodName>` выбери или создай `<ClassName>_<camelCasedMethodName>`.
- Называй контейнер модульных тестов класса `<TargetClassName>Test`, а контейнер тестов чистой функции верхнего уровня — `<PascalCasedFunctionName>Test`.
- Для SUT с уточнённым вариантом переиспользуй только единственный существующий контейнер, соответствующий выбранному виду теста, SUT без уточнения варианта и точному варианту, сохраняя его файл и вложенность и пропуская описанный ниже вывод контейнера и пути; при нескольких совпадениях остановись, а при отсутствии совпадений примени правило выбранного вида теста к SUT без уточнения варианта.
- Однозначно определи владельца кода SUT: указанный класс или функцию для компонентных и модульных тестов, а для граничных тестов — точку входа в код, соответствующую идентификатору внешней операции.
- Размещай новый контейнер в модуле владельца кода, соответствующем наборе исходников тестов и пакете; если в модуле несколько наборов исходников тестов, используй принятый для выбранного вида теста и остановись, если его нельзя определить однозначно.
- Если выведенный контейнер уже существует по этому расположению, добавь кейс в него; иначе создай там соответствующий файл.

## Отображаемые имена и методы

- Помещай человекочитаемый текст класса и кейса в `@DisplayName`.
- Пиши на настроенном `artifact_language` только отображаемый текст; сохраняй стиль репозитория для технических идентификаторов.
- Задавай `@DisplayName` класса по соответствующему `Feature`; иначе называй его по контейнеру поведения, функциональности, операции или методу API и добавляй ссылку на SUT по загруженным правилам именования Feature.
- В компонентных тестах человекочитаемая часть может называть проверяемое поведение, если ссылка на SUT в скобках идентифицирует определённый компонент.
- Задавай `@DisplayName` кейса как начинающееся со строчной буквы продолжение `@DisplayName` класса, описывающее наблюдаемое поведение или свойство результата; для русского языка используй `должен` или `должна`.
- Размещай условие на входные данные или состояние перед обязательством либо после требуемого результата; используй язык бизнеса, конечного пользователя и публичного контракта, сохраняй необходимые технические термины и избегай случайных деталей реализации.
- Для тестов на наборах данных называй кейс по общему инварианту, а изменяемое измерение выноси в параметризованное отображаемое имя.
- Для методов кейсов используй `test_<slug>`, где slug — краткое описание из 2–5 слов в формате ASCII `snake_case` в нижнем регистре; при коллизии остановись.

## Сопоставление с формальными кейсами

- Применяй формальное сопоставление, определённое в `../core/test-naming.md`.
- Если формальное сопоставление применимо, но `Feature` или `Rule` нельзя уверенно восстановить, остановись и сообщи об отсутствующей точке привязки.
- Для формальных артефактов задавай `@DisplayName` класса исходным текстом `Feature` без `Feature:`, а `Rule` и именованный `Example` копируй, удаляя только префикс заголовка, одно двоеточие и окружающие пробельные символы.
- Остановись, если `Rule` не начинается со строчной буквы или любой из двух исходных текстов содержит `::`.
- Для набора, подходящего для параметризации, используй `<rule>` как `@DisplayName` метода, а точный заголовок каждого именованного `Example` — как отображаемое имя вызова.
- Для формы `property` используй `<rule>` как `@DisplayName` метода и сохраняй именованный `Example` как метаданные генерируемых входных данных.
- Если `Example` именован и не относится к параметризованной форме или форме `property`, используй `<rule> :: <example>`; если `Example` не именован, отсутствует или пуст, используй `<rule>`.
- Используй `@Nested`, только если существующий файл уже группирует связанные кейсы таким способом.
- Для `strengthen` или `extend-parameterized` сохраняй записанный идентификатор метода.
