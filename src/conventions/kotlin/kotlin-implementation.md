# Реализация на Kotlin

- Общие правила
  - Предпочитай функциональный стиль: неизменяемые данные, чистые функции и преобразования через `map`/`filter`, когда они сохраняют ясность кода.
    - Предпочитай `val` для полей и локальных переменных.
    - Не используй нуллабельные типы, когда их можно заменить другими конструкциями языка (например, `lateinit` и `by lazy`) или дизайном (например, алгебраический тип, вместо класса с взаимоисключающими нуллабельными полями).
    - Если поведение не зависит от состояния класса, реализуй его верхнеуровневую функцию (top-level function).
      Если подобных сильно связанных (high cohesion) функций несколько - сделай их методами объекта-синглтона.
    
- Форматирование и стиль кодирования
  - Добавляй пустые строки после заголовка класса и вокруг каждого метода.
    - Не добавляй и не удаляй пустые строки в уже существующих блоках кода.
  - Используй `artifact_language` для комментариев в коде.
  - Предпочитай синтаксис операторов Kotlin прямым вызовам `operator fun`.
  - Предпочитай Kotlin материализованные дженерики эквивалентным Java overloads с `Class<T>`, когда они доступны.
  - Используй Kotlin тела-выражения (expression bodies), только если всё представленное поведение работает быстро и безопасно: является функционально чистым либо ограничено быстрыми безопасными чтениями глобального окружения, например текущим временем или переменными окружения (environment variables).
    - Считай работу, отложенную через лямбды, Kotlin-последовательности (Sequences), Java-потоки (Streams), объекты Futures или похожие ленивые значения, частью представленного поведения; 
      используй тела-блоки, если любая представленная работа выполняет другой I/O, изменяет наблюдаемое состояние, может блокироваться или владеет жизненным циклом какого-либо ресурса (файла, потока, мьютекса, подключения к БД и т.п.).
  - Используй именованные аргументы для констант и переменных, имя которых отличается от имени соответствующего параметра.
  - Импорты
    - Не оставляй Fully Qualified Names в местах использования Kotlin - импортируй их, а в случае конфликта неквалифицированных имён используй алиасы при импорте.
    - Не меня способ импорта (wildcard и перечисление всех импортируемых классов) если это не требуется запросом пользователя или линтером.

- Дизайн API
  - Используй значения по умолчанию только в двух случаях:
    - сохранение обратной совместимости опубликованного API.
    - когда больше половины клиентов используют одно и то же значение и случайный пропуск указания значения безопасен - то есть отсутствие значения не запускает опасные побочные эффекты.
      Примеры опасных побочных эффектов: удаление или деструктивное изменение данных, обращение к внешним системам которые, которые стоят владельцу или пользователю продукта существенных денег или репутационных рисков, либо действие которых сложно отменить.
