# Подготовка к написанию теста

На этом этапе определи, как реализовать выбранный тест, но пока не меняй файлы репозитория.
Сохраняй решения только во внутреннем контексте `$code-test-case`: не создавай отдельный документ с планом и не предлагай планирование как самостоятельную операцию.

Изучай только те части репозитория, которые нужны для решений ниже.

## Что и где изменить

1. Исходи из выбранного SUT и уже проверенных решений о виде и форме теста и о том, какой тест нужно создать или изменить.
2. Примени раздел «Сопоставление при кодировании» из `framework_checkout_root/src/conventions/core/test-case-selection.md`.
3. Определи, через какое API тест будет вызывать проверяемое поведение, в следующем порядке:
   - API, указанное при вызове скилла;
   - существующее API, через которое можно однозначно вызвать нужное поведение SUT;
   - новое API, если его сигнатуры и типы однозначно следуют из кейса, переданного контекста и соглашений репозитория.
4. Найди подходящие тестовые API, фикстуры и функции проверки.
   Если их недостаточно, определи минимальные дополнения.
5. Для `new` определи файл и тестовый класс или другую принятую во фреймворке группу тестов по виду теста, SUT и соглашениям об именовании.
6. Для `strengthen` или `extend-parameterized` найди именно указанные файл, группу тестов и тестовый метод; не выбирай вместо них другой тест.

## Параметризованный тест

Реализуй `Scenario Outline` одним параметризованным тестовым методом.
Столбцы `Examples` задают входные данные и ожидаемые результаты, каждая строка — отдельный запуск.
При `strengthen` и `extend-parameterized` сохраняй существующие наборы параметров.
Предусмотри выполнение всех строк выбранного шаблона так, чтобы по результатам было понятно, какие строки прошли, а какие упали.
Передавай разные ожидаемые результаты через параметры, без условных выражений и ветвлений в теле теста.

## Когда остановиться

Сообщи, что мешает продолжить, вместо того чтобы угадывать решение, если:
- непонятно, какой SUT и какое требование проверять, какой тест создать или изменить, как запустить именно его или какие изменения разрешены;
- выбранный кейс противоречит переданному контракту;
- новое или изменяемое публичное API можно спроектировать несколькими корректными способами, а готовое решение не передано;
- для компиляции нужно добавить API основного кода, но его сигнатуры и типы нельзя однозначно определить из предоставленных данных;
- из кейса и соглашений непонятно, как реализовать необходимые фикстуры, тестовые API или функции проверки;
- по переданным сведениям о репозитории нельзя определить надёжный способ скомпилировать и запустить именно выбранный тест.

Передай решения или причину остановки обратно в `$code-test-case`, не меняя репозиторий.
