# Именование Feature

Именуйте `Feature` как `<человекочитаемый проверяемый объект> (<Техническая ссылка на SUT>)`.

Используйте подтверждённую доказательствами SUT-ссылку и не придумывайте её.
Подтверждайте её явными входными данными, существующими артефактами, кодом или предоставленным дизайном.
Не придумывайте имя или адрес проверяемого объекта по описанию желаемого поведения и не подставляйте заглушку вместо неизвестной ссылки.
Если SUT-ссылку нельзя установить, остановитесь и сообщите об отсутствующей точке привязки.

Для HTTP-границы начинайте русскоязычную человекочитаемую часть с `Метод API`, затем указывайте назначение операции.
Указывайте SUT-ссылку HTTP-границы как `<HTTP method> <path>`.

Для другой границы используйте её устойчивый внешний идентификатор операции: например, команду, топик, имя очереди, маршрут, команду CLI, внешнюю операцию и т. п.

Для тестов, работающих с SUT напрямую, используйте `<ClassName>`, если они проверяют поведение двух или более методов, и `<ClassName>.<methodName>`, если проверяют только один метод.
Для функции верхнего уровня используйте её точное имя из фактического кода или предоставленного дизайна.

Для поведения, относящегося к одному полиморфному варианту, добавляйте `, <exact variant reference>` внутри скобок SUT.
Считайте SUT-ссылку обязательной точкой привязки к коду, а не случайной технической деталью для абстрагирования.

## Примеры

Условные имена SUT для разных способов проверки:

| Что проверяют тесты | Заголовок |
| --- | --- |
| Создание заказа через HTTP | `Feature: Метод API создания заказа (POST /orders)` |
| Обработку сообщения очереди | `Feature: Обработчик нового заказа (orders.create)` |
| Совместное поведение `addItem` и `removeItem` | `Feature: Заказ (Order)` |
| Только метод `total` | `Feature: Метод расчёта стоимости заказа (Order.total)` |
| Функцию верхнего уровня | `Feature: Функция расчёта скидки (calculateDiscount)` |
| Обработку одного варианта платежа | `Feature: Обработчик оплаты картой (PaymentProcessor.process, CardPayment)` |
