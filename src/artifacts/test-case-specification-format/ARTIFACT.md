# Формат спецификации тест-кейсов

## Цель

Описывайте проверки требований кратким контрактным текстом.
Используйте один формат для вывода и ревью требований, проектирования и написания исполнимых тест-кейсов, а также обратной разработки по тестам.

## Структура

Перед формированием `Feature` прочитайте `references/feature-naming.md`.
Используйте один `Feature` для одной конкретной конечной точки, API-поверхности, компонента, операции или другого проверяемого объекта.
Используйте один `Rule` для одного внешне наблюдаемого обязательного свойства, инварианта, отказа, побочного эффекта или обязательства по результату.
Используйте именованный `Example` только для перечисления существенно разных классов входных данных или контекста для одного `Rule`.
Один `Example` может вместо этого описывать класс входных данных и свойство, обязательное для каждого его элемента.
Используйте безымянный `Example` только как контейнер случая полного режима, когда имя примера не нужно.
Если у `Rule` есть безымянный `Example`, этот безымянный пример должен быть единственным `Example` в этом `Rule`.
Не используйте `Example` для независимых свойств.
Сохраняйте один уровень абстракции внутри одного `Feature`.
Пишите `Rule` в форме обязанности языка артефакта, если в нём есть такая форма.
Для русского `Rule` используйте `должен` или `должна`.
Размещайте условие входных данных или состояния либо перед обязанностью, либо после требуемого результата.
Описания в простом настоящем времени не соответствуют формату, кроме случаев, когда они в точности повторяют формулировку публичного контракта.
Пишите весь человекочитаемый текст на настроенном `artifact_language`.
Используйте только английские ключевые слова `Feature`, `Rule`, `Example`, `Given`, `When`, `Then` и `And`.
Перед формированием прочитайте `references/layout.md`.

## Необязательная ссылка на источник

Блок `Rule` или `Example` может содержать не более одной необязательной ссылки на источник.
Считайте её метаданными, а не шагом `Given` / `When` / `Then`.
В простом тексте артефакта размещайте машинную форму сразу под `Rule`, если `Example` не выводится, или сразу под соответствующим `Example`.
Если окружающий контейнер поддерживает кликабельные ссылки, те же метаданные можно выводить в понятной человеку форме контейнера вне блока исходного артефакта.
Прочитайте `references/source-reference.md`.

## Режимы

У этого артефакта ровно два режима:
- `short`
- `full`

Оба режима требуют `Feature` и `Rule`.
`short` сохраняет только строки `Feature`, `Rule` и необязательного именованного `Example`.
Если у `Rule` в `full` ровно один безымянный `Example`, опускайте этот `Example` в `short`.
`full` добавляет один или несколько блоков `Example` с `Given`, `When`, `Then` и `And` под каждым `Rule`.
В `full` безымянные примеры выводятся как `Example`.

Читайте правила режимов в:
- `references/mode-short.md`
- `references/mode-full.md`

## Общие правила содержания

За пределами материализованной SUT-ссылки `Feature` описывайте только внешне наблюдаемое контрактное поведение.
Используйте предметный язык для человекочитаемого имени `Feature`, `Rule`, `Example` и шагов.
За пределами материализованной SUT-ссылки `Feature` упоминайте технические детали только когда это наблюдаемые условия контракта и устойчивой предметной формулировкой нельзя выразить то же поведение.
Если параметр запроса, поле, флаг, значение enum, статус, метка времени или другой технический символ имеет устойчивый предметный смысл, пишите этот смысл вместо буквального символа.
Не сохраняйте литерал только потому, что он встречается в API, хранилище, коде или тестах.
Сохраняйте буквенные символы, только когда требование относится именно к этому члену контракта или значению, ясного предметного эквивалента нет либо замена потеряет проверяемую точность.
Оставляйте только видимые в контракте требования к интерпретации запроса, авторитетным источникам данных, логике принятия решения, области и выборке результата, обязательным свойствам ответа или возвращаемого значения, порядку, кардинальности, изменениям состояния, побочным эффектам, условиям отказа, явным инвариантам и представлению видимых в контракте значений.
За пределами материализованной SUT-ссылки `Feature` не упоминайте структуру реализации, схему хранилища, имена helper-ов, mocks, fixtures или шаги миграции.
Не придумывайте маршруты, статусы, значения по умолчанию, валидацию, резервное поведение или внутреннее устройство.
Сохраняйте буквальные значения, различающие поведение, если они являются частью контракта.
В остальных случаях предпочитайте абстрактные формулировки случайным тестовым данным.
Объединяйте почти дублирующие правила и примеры в минимальный полный набор без избыточности.
