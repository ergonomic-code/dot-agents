# Идемпотентность миграции создания функции

## Обстоятельства и свидетельства

В процессе работы агент создал миграцию с добавлением функции без `OR REPLACE`.

Обезличенный фрагмент миграции:

```sql
CREATE FUNCTION public.matches_device_serial(serial_number varchar)
RETURNS boolean
LANGUAGE sql
IMMUTABLE
STRICT
PARALLEL SAFE
AS $$ SELECT serial_number LIKE 'X%' $$;
```

Запрос на исправление фреймворка: «Общее правило - миграции всегда надо делать идемпотентными, когда это возможно».
Ожидаемое поведение — обеспечивать идемпотентность миграций доступным для БД способом с сохранением требуемого результата.
В PostgreSQL `CREATE FUNCTION` не поддерживает `IF NOT EXISTS`; выбор между `CREATE OR REPLACE FUNCTION` и условным созданием зависит от смысла изменения.
Основание: [документация PostgreSQL](https://www.postgresql.org/docs/current/sql-createfunction.html).

## Причина и границы выводов

Подтверждён пробел контекста: в соглашении миграций отсутствовало требование идемпотентности.
Отсутствие сессии создания миграции не позволяет установить, какой контекст прочитал её автор и почему он выбрал обычный `CREATE FUNCTION`.

## Выбранное исправление

Выбран оптимальный вариант: в `src/conventions/database/db-schema-migrations.md` добавлены общее требование идемпотентности и требование выбирать поддерживаемый БД способ без повторения изменений данных или сокрытия несовместимого состояния схемы.
Остальной человекочитаемый текст соглашения переведён на русский с сохранением прежних правил.
Правило остаётся в существующем соглашении миграций, доступном через индекс реляционных БД; отдельная маршрутизация и расширение проверочного процесса не нужны.
