# Источники ожиданий параметризованного теста

## Свидетельства

Сессия: `01a186ba-4643-7da0-8b0d-34b2a918e2b2`.
Параметризованный кейс одновременно сравнивал результат с ожиданием из фикстуры и с ожиданием из параметров варианта.
Связь входа и ожидаемого результата была распределена между источником параметров и реализацией хелпера.

Релевантные запросы пользователя, обобщённый пересказ:

- В параметризованном тесте задавать каждое ожидание либо общим для всех вариантов и независимым от параметров, либо полностью определяемым параметрами варианта.
  Определять входные данные и ожидаемый результат рядом, кроме тривиальных случаев, чтобы их связь была очевидной.

## Проблемный код

Сокращённая обезличенная реконструкция: имена и значения заменены, сохранены два источника ожиданий.

```kotlin
fun variants() = Stream.of(
    namedArguments("ниже диапазона", Range(10.0, 20.0), 9.0, Status.LOW),
    namedArguments("выше диапазона", Range(10.0, 20.0), 21.0, Status.HIGH),
)

@ParameterizedTest
@MethodSource("variants")
fun test_warning(range: Range, value: Double, status: Status) {
    // Given
    val fixture = installer.install(fixtureFor(range, value))

    // When
    val result = api.getState()

    // Then
    result.warning shouldBe fixture.warning
    result.warning?.status shouldBe status
}
```

Диапазон передан параметром, но полное ожидание берётся из фикстуры, а ожидаемый статус — из строки варианта.
Первое сравнение добавляет ожидания, не заданные рядом со входными данными в источнике параметров.

## Целевой код

Этот кейс проверяет выбор статуса по диапазону и значению.
Ожидаемый статус задан рядом с ними в каждой строке параметров; дополнительное ожидание из фикстуры удалено.


## Контекст и причина

В сессии есть вызовы чтения `src/context/tests.md` и соглашений `test-design.md`, `test-fixture-architecture.md`, `test-implementation.md` из `src/conventions/core/`.
Сам факт вызова не подтверждает полноту прочитанного контекста: объём вывода был ограничен.
Подтверждённый пробел соглашений до исправления — отсутствие ограничения источников ожиданий параметризованного кейса.
Требование задавать ожидания в `Given` также не называло источник параметров допустимым местом определения.
Пропуск маршрутизации как причина не подтверждён.

## Исправление

- В `test-implementation.md` закреплены совместное определение входа и ожидания и два допустимых источника ожиданий параметризованного теста.
  Указания про `Given` согласованы с использованием источника параметров.
- В `test-implementation-checklist.md` согласована проверка ожиданий.
