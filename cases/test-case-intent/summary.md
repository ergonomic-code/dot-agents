# Намерение кейса и применение замечаний

## Свидетельства

Источник: сессия `01a186ba-4643-7da0-8b0d-34b2a918e2b2`.
Пользователь просил привести в порядок тесты, затем распространить замечания на остальные кейсы текущей области работы (пересказ).
Последующие замечания требовали убрать лишние объекты фикстуры, генерировать несущественные значения, вычислять связанные значения, задавать ожидания рядом со входом и переиспользовать намерение вместо случайных совпадений (пересказ).
Агент исправлял отдельные места, после чего пользователю приходилось повторно указывать аналогичные проблемы.

Агент читал индекс тестов, соглашения о дизайне, реализации, архитектуре фикстур, рефакторинге и чек-листы.
Вывод части чтений усечён, поэтому полная загрузка всех инструкций не подтверждена.
В сохранённом выводе видны правила о значимых данных, вычислении связанных значений и обязательном выделении хелпера при дублировании более трёх строк.

## Причина и ожидаемое поведение

Правила о данных были доступны, но применялись непоследовательно.
Механический порог выделения хелпера конфликтовал с выбором абстракции по смыслу.
Явного требования распространять замечание на все аналогичные места текущей области работы не было.
Нужны определение намерения перед правкой и пересмотр затронутого кейса целиком после неё.

## Обезличенный пример

Схематическая реконструкция ошибки: фабрика создаёт лишнее событие, которое затем подменяется; ожидание остаётся связанным с исходной фикстурой.

```kotlin
val base = sampleFixture()
val events = listOf(event(id = fixedId), event(id = otherFixedId))
namedArguments("выбор последнего", base.copy(events = events), base.result)
```

Целевой вариант: вход и ожидание описывают один сценарий, несущественный идентификатор генерируется, существенная связь вычисляется.

```kotlin
val first = event(id = faker.uuid())
val last = event(id = first.id.next())
namedArguments("выбор последнего", fixture(events = listOf(first, last)), resultOf(last))
```

Оба варианта передают фикстуру и полное ожидание одному методу кейса, который устанавливает фикстуру, вызывает проверяемую операцию и сравнивает её результат с переданным ожиданием.
Имена и API в примере условные; он иллюстрирует связь данных, а не реализацию генератора или сравнения идентификаторов.

## Исправление

Выбран оптимальный вариант: намерение закреплено в дизайне, правила данных и переиспользования — в реализации, пересмотр целого кейса — в чек-листе.
Удалён порог в три строки, а загрузка соглашения реализации распространена на источники параметров, фикстуры, помощники и адаптеры.

Новые соглашения и ключевые слова не добавлены.
