# Тесты на тестовый хелпер

## Обстоятельства и ошибка

Запрос пользователя (обобщённый пересказ): получать базовый UUID из faker и добавить тестовый хелпер увлечения его на единицу с исключением при переполнении.
Агент добавил хелпер в тестовую инфраструктуру, применил его в существующих сценариях и создал отдельный класс тестов самого хелпера.
Ожидаемое поведение — изменить хелпер и его использования, проверив их существующими тестами системы без добавления тестов на тестовый код.

Свидетельство: сессия `01a186ba-4643-7da0-8b0d-34b2a918e2b2`, патч с добавлением хелпера и отдельного класса тестов, команда их запуска и итоговый ответ агента.
В сессии прочитаны индекс тестов, соглашения о дизайне, выборе кейсов, реализации тестов, архитектуре фикстур и рефакторинге тестов.

## Причина

В загруженном контексте отсутствовал запрет тестировать тестовый код.
Правило покрытия требовало проверять каждую добавленную операцию и вычисление без ограничения рабочим кодом.
Это подтверждённый пробел контекста; применение именно этого правила как мотива агента остаётся гипотезой.

## Пример

Обезличенная сокращённая реконструкция ошибки: тестовый хелпер стал самостоятельным SUT.

```kotlin
// Тестовый хелпер
operator fun UUID.plus(increment: Long): UUID = incrementChecked(this, increment)

// Отдельный тест тестового хелпера
@Test
fun rejectsOverflow() {
    shouldThrow<ArithmeticException> { maximumUuid + 1 }
}

// Использование в подготовке существующего теста системы
val firstId = faker.randomUuid()
val secondId = firstId + 1
```

Целевой вариант (реконструкция): сохранить хелпер и его использование в подготовке теста системы, не добавлять отдельный тест хелпера.

```kotlin
operator fun UUID.plus(increment: Long): UUID = incrementChecked(this, increment)

// Подготовка данных существующего теста системы
val firstId = faker.randomUuid()
val secondId = firstId + 1
```

## Исправление и проверка

Выбран оптимальный вариант: запрет в `src/conventions/core/test-design.md` и ограничение покрытия рабочим кодом в `src/conventions/core/test-implementation.md`.
По уточнению пользователя каноническое определение операции системы в `src/conventions/ergonomic-architecture/ergonomic-component-structure.md` описывает метод-оркестратор, вызываемый напрямую из порта.
Правило покрытия ссылается на это определение.
В рабочем словаре собственного `AGENTS.md` закреплён термин «рабочий код» вместо «производственный код».
Индекс `src/context/tests.md` всегда подключает дизайн тестов при работе с тестами и хелперами; изменение маршрутизации не требуется.
Проверены diff, согласованность с архитектурной терминологией и существующая маршрутизация.
Изменения касаются инструкций; новые автоматические тесты не добавлялись.
README не требует синхронизации: возможности, установка и точки входа фреймворка не меняются.
