# Сохранение формулировки при усилении кейса

## Свидетельства

Сессия: `01a12fab-1800-74c3-a8c1-9178dc254e28`.
Пользователь запросил кодирование пробела покрытия G03 из аудита тестов перед рефакторингом хранения ролей.
Релевантная часть исходного запроса; абсолютный путь к аудиту обезличен:

```text
371-1

/$code-test-case

g03
[@020-test-audit.md](<путь к аудиту>)
```

После сообщения о недостающей спецификации пользователь уточнил:

```text
ок, напиши сначала спеку
```

Агент выбрал `strengthen` для существующего теста подтверждения email, но заменил его исходное правило новым правилом о ролях:

```diff
- Rule: при передаче корректного токена должна создавать профиль и дефолтные теги и разрешать пользователю доступ к эндпоинтам роли User
+ Rule: при подтверждении email должен заменять DemoUser на User с сохранением остальных ролей
```

Пользователь исправил агента:

```text
правило надо оставить как есть - ты же усиливаешь существующий тест, не меняешь его
```

После замечания агент восстановил исходный `Rule` дословно и включил прежние проверки профиля и тегов вместе с дополнительными проверками ролей.
Ошибка наблюдалась в спецификации; код теста в этой сессии не изменялся.
Ожидается сохранение исходной формулировки и обязательств; при необходимости допускается только дополнение новым требованием без переписывания исходного текста.

## Причина

Загружены `code-test-case`, `design-test-case`, `write-verification-check`, соглашения `test-case-selection`, `test-naming`, применимые индексы тестов и HTTP API, правила проектирования и references формата спецификации.
Исходное отображаемое имя теста прочитано до формирования ошибочного `Rule`.
Проблема в формулировке контекста: `test-naming` требует сохранять исходный текст, но описывает именование и формальное сопоставление, а не явно проектирование усиления.
`test-case-selection` сохраняет смысл вызовов и существующие проверки, но не закреплял дословное сохранение правила при `strengthen`.
Шаг проектирования в `design-test-case` предлагал заново сопоставить выбранное обязательство с `Rule`, не выделяя существующую формулировку как источник для усиления.
Сессия подтверждает чтение правил и замену формулировки; внутреннюю причину решения агента она достоверно не объясняет.

## Исправление

Выбран оптимальный вариант.
`src/conventions/core/test-case-selection.md` закрепляет сохранение исходной формулировки и всех обязательств при `strengthen`, разрешая только дополнение новым требованием.
Шаг проектирования в `src/skills/design-test-case/SKILL.md` восстанавливает исходный `Rule` из существующей спецификации или названия выбранного теста и применяет это соглашение.
Оба изменённых файла полностью переведены на русский с сохранением технических значений.
В скилле длиннее 50 строк заменён существующий шаг: восстановление исходного правила относится непосредственно к алгоритму проектирования, а само правило остаётся в уже загружаемом соглашении.

## Проверка

`pytest -q`: 148 тестов прошли.
`git diff --check`: ошибок нет.
Ревью по `review-framework-changes`: `ok`.
При разборе исходного сценария проверено: шаг проектирования теперь берёт исходное правило о профиле, тегах и доступе, а соглашение требует сохранить его текст и прежние обязательства при добавлении проверок ролей.
Для сценария дополнения правила соглашение разрешает добавить новое требование только с сохранением исходного текста; замена исходного правила формулировкой о ролях этому условию не соответствует.
Проверки подтверждают согласованность инструкций; повторная работа агента в целевом проекте с исправленным контекстом не проводилась.
README не требует синхронизации: уточняется существующее поведение `strengthen`, без изменения возможностей, установки, поддерживаемой области или точек входа.
Связи сохранены: `design-test-case` и `code-test-case` читают изменённое соглашение; `test-naming` сохраняет исходный текст, а `code-test-case` сохраняет существующие проверки и вызовы.
