# Именование тестов HTTP-границы

## Свидетельства

Сессия: `01a0fc61-082c-7b33-a742-e341571f165b`.
Исходный запрос пользователя:

```text
370

подчисти module
```

При замене SQL-фикстур тестовыми хелперами агент добавил отображаемые имена класса HTTP-тестов и его кейсов.
Обезличенный фрагмент результата:

```kotlin
@DisplayName("Получение объектов (ObjectsController.getObjects)")
class ObjectsTest {
    @DisplayName("должно возвращать объекты, изменённые после последней синхронизации")
    // ...
}
```

Ожидается русскоязычное имя группы `Метод API <назначение операции> (<HTTP method> <path>)` и продолжающие его имена кейсов с `должен`.
HTTP-метод и путь должны подтверждаться кодом или контрактом.

## Причина

Подтверждён пробел в контексте: обязательного префикса `Метод API` не было ни в прочитанных правилах JUnit, ни в общем справочнике именования `Feature`.
Загружены индексы тестов, ergonomic-testing, Kotlin, JUnit, HTTP API, а также применимые правила реализации, именования JUnit и HTTP-хелперов и чеклисты.
Дополнительно подтверждён пробел в маршрутизации: общий справочник `feature-naming.md` не прочитан после решения добавить `@DisplayName`.
В результате имя содержит ссылку на метод контроллера вместо требуемой HTTP-ссылки.
Почему агент не повторил классификацию работы после добавления имён, сессия достоверно не объясняет.

## Исправление

Выбран оптимальный вариант.
Единый справочник именования `Feature` задаёт префикс для русскоязычного имени HTTP-границы; существующие правила JUnit используют его и для `@DisplayName`.
Индекс тестов задаёт условие загрузки правил по добавлению или изменению имён тестовых групп и кейсов, независимо от тестового фреймворка и вида работы.
HTTP-чеклист проверяет префикс и HTTP-ссылку в имени группы.
Это охватывает формальные спецификации и код тестов без дублирования правила в соглашениях JUnit.

## Проверка

`pytest -q`: 107 тестов прошли.
`git diff --check`: ошибок нет.
Проверены существующие связи: индекс тестов загружает общий справочник, JUnit использует его при именовании, формат спецификации читает его перед формированием `Feature`, а HTTP-индекс вызывает изменённый чеклист.
Проверки подтверждают структуру контекста; повторная работа агента в целевом проекте с новым правилом не проводилась.
README не требует синхронизации: уточняется существующее соглашение об именовании, без изменения возможностей, установки, поддерживаемой области и точек входа, описанных в README.
