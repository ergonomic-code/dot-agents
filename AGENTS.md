# AGENTS.md

## Назначение

Этот файл регулирует работу над самим фреймворком.
Работа над контекстом фреймворка создаёт и изменяет файлы, которые регулируют работу агентов в целевом репозитории.

## Работа с задачами

Для работы над самим фреймворком `framework_checkout_root` — корень текущего репозитория.
Прочитай `src/task-workdir/entrypoint.md` и выполни подключение контекста задачи.

## Референсы Эргономичного подохода

При наличии прочитай корневой `AGENTS.local.md`: он содержит ссылки на локальные копии и дополнительные репозитории.
Используй релевантные [референсы ЭП](.agents/references/ergonomic-programming.md) для получения дополнительного контекста, прояснения терминов, поиска примеров и сверки решений, идей и предложений с реальным кодом.
ЭП всё ещё в разработке; материалы и код могут содержать уже отброшенные примеры, идеи и решения.
Не считай найденное автоматически актуальным правилом ЭП, особенно если это было написано более 6 месяцев назад; при сомнениях уточняй актуальные правила у пользователя.

## Язык контекста фреймворка

Пиши контекст фреймворка на русском.
Пиши новые контекстные файлы фреймворка на русском.
При изменении существующего контекстного файла фреймворка переводи на русский весь его человекочитаемый текст, включая неизменённые фрагменты.
Не переводи технические идентификаторы, пути, код, команды, ключи форматов, имена API и дословные контрактные значения, если перевод изменит их смысл или нарушит работоспособность.
Фреймворк находится в процессе постепенного перевода с английского на русский, поэтому не затронутые текущей работой файлы могут оставаться на английском.

## Краткость

Ставь корректность, необходимый контекст и проверяемость выше краткости.
После выполнения этих требований пиши кратко.
Пиши простым, естественным языком и связывай мысли в последовательное объяснение.
Предпочитай меньший объём содержания, сохраняя связность изложения; допустимо немного увеличить текст, если так он читается легче.
При изменении файлов фреймворка предпочитай минимально достаточную правку и не добавляй предупредительные правила без необходимости.
Минимальность оценивай среди решений, соответствующих ответственности компонентов и области применения правила.

По умолчанию не добавляй поясняющие примеры.
Добавляй их по явному запросу пользователя или для устранения конкретной неоднозначности, которую трудно устранить короткой правкой формулировки.
Без явного запроса ограничивайся одним коротким примером на такую неоднозначность; при сомнении обходись без примера.

## Архитектурные решения

До рекомендации архитектурного решения исследуй релевантные файлы: ответственность компонентов, область применения и ограничения зависимостей.
При выборе места нового правила представь альтернативы размещения: подходящие существующие компоненты и, если их ответственности недостаточно, дополнение структуры.
Для каждого варианта укажи соответствие ответственности и области применения, а также решающее преимущество или ограничение относительно остальных.
Объём правки и удобство загрузки учитывай после этого сравнения.
Место правила выбирай по ответственности и области применения; отдельно проверяй, как оно будет загружаться.
Предложения пользователя оценивай по тем же критериям; при смене рекомендации объясняй, какой новый факт или ранее упущенное ограничение изменило вывод.

Для локальной правки, не затрагивающей распределение ответственности, зависимости или область применения, отдельный разбор альтернатив не нужен.

## Управляющие файлы фреймворка

Управляющие файлы фреймворка находятся в `.agents/`.
Выбирай скилл для исправления файла по его каноническому пути после разрешения симлинков.
Для исправления контекста, поставляемого фреймворком целевым проектам, используй `.agents/skills/fix-framework-context/SKILL.md`.
Для исправления `AGENTS.md`, `.agents/**` и `.codex/**` самого репозитория фреймворка используй `.agents/skills/fix-self-context/SKILL.md`.
Сами по себе файлы под `src/` не являются активными управляющими файлами фреймворка; для работы с задачами явно подключён `src/task-workdir/entrypoint.md` и его зависимости.

# Соглашения Markdown

## Структура текста

Разделяй самостоятельные темы на разделы и подразделы с содержательными заголовками.
Внутри темы оформляй перечисления списками из коротких пунктов; длинные пункты разбивай на подпункты.
В прозаических абзацах начинай каждое предложение с новой строки.

## Компактное форматирование

Форматируй Markdown компактно.
Используй пустые строки только между заголовками и абзацами.
Не разделяй предложения пустыми строками.

Но при этом разделяй текст на целостные абзацы.
Один абзац может состоять из одного длинного, логически целостного предложения.

## Тесты Python

Запускай тесты командой `pytest -q`.
Не добавляй тесты, которые проверяют конкретную человекочитаемую формулировку в файлах соглашений.
Проверяй структурный или машинно-проверяемый инвариант и используй точное сравнение только для технических или контрактных значений, точное написание которых само является контрактом.
